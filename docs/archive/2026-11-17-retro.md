# Jump Attack 项目复盘与 3 版方案

## 结论

真正要修的不是代码，也不是 PR 流程，而是**做功能和真实验证之间断了线**。17 天里合了 54 个 PR、46 个新功能提交，可真机验证读数是 0 条（`validation/读数.txt` 还是空模板），所有测量的误差都只在合成视频上验过。返工、慢 PR、接手难，都是这一个根因的不同表现。

还有一个更值得先看的事实：你离扣篮线只差约 2 cm，这已经接近摸高读数本身的误差。接下来两周决定成败的是训练、减量和真实扣篮尝试，而不是 App 再多一个功能。

推荐**方案 B「先验证，后加功能」**：12/1 前冻结新功能；搭在你本来就要做的一次测试上，多拍一轮，把现有测量分成「真机验证过」和「没验证」，没验证的指标不参与「差在哪块」的判断；再把这条做成规则、CI 检查和一个 Skill。我这边大约 1 天，你只需要在下次测试时多拍 20 分钟。

## 问题重新定义

这 10 条大多在问“开发怎么更好”，这是手段。目标有两个：12/1 前扣进去；以后推广到队内时，别人能信 App 给的数。用这两个目标去看，很多“问题”其实是症状。

| 看到的症状 | 背后的原因 |
| --- | --- |
| 起跳技术连续 68 个 `fix(technique)` | 误差算法只能对着合成视频调，没有真实标准答案，也没有事先定好“够好了”的线，所以停不下来 |
| 几个 PR 卡了好几天 | 在等你确认阈值；但没有真实数据，你其实也判断不了阈值对不对 |
| 大多数 PR 写着“未真机验证” | 验证只能靠你一个人拿手机做，这份产能接近 0，而功能由多个 Claude 线程并行产出，几乎零成本 |
| 接手难、代码多 | 3.2 万行源码，很多是在核心测量被验证前就铺开的广度（网页版、三语、团队模式、落地页、宣传片） |
| 11-05 之后停更 | 仓库里看不出来。可能是在练，也可能 App 没真正用起来。项目规定不加统计上报，所以只能问你 |

最深的一层是成本不对称：加一个功能对 Claude 几乎免费，验证一个功能却要你亲自去场地拍。没人管这个不对称时，系统天然往“多做”倾斜。

一个我确认不了的前提：你实际用了哪些功能。下面按“基本没在真机上用”分析；如果你其实天天在用，结论会变成“反馈有，但没回到仓库里”，方案 B 照样成立。

## 接手成本

一个很强但不了解项目的工程师，大概要 2–3 天才能放心改测量代码。最贵的不是代码量，而是\*\*“为什么”都不在仓库里\*\*。

| 地方 | 为什么难懂 | 简化办法 |
| --- | --- | --- |
| 决策依据 | 阈值来源指向 claude.ai 上的「扣篮导向方案」，误差报告、审查清单都在 Artifact 里，还有 35 个项目记忆文件。新人一个都打不开 | 仓库里加 `docs/decisions/`，每个阈值和关键取舍一条短记录 |
| 同一个量有好几条路 | 跳跃高度可以来自手动标帧、`autoMark` 像素识别、`poseJump` 骨架找跳、`jumpAnalysis`（仿 Arcus）、`technique` 的 vz²÷2g。先要搞清哪个页面用哪条，哪个数进诊断 | metrics 注册表里给每个指标标上来源管线和验证状态，一张表看懂 |
| `technique.ts` | 1445 行、35 次提交，和 `techniqueRead`、`techniqueText` 三件套。误差一层套一层 | 按步长 / 速度 / 误差传播拆文件（仅方案 C） |
| `domain/` 平铺 52 个文件 | 看不出哪些服务三问、哪些是辅助 | 按三问分子目录：差多少 / 差在哪 / 练什么 / 测量 / 辅助（仅方案 C） |
| 命名 | 两个 `analyse` 页（measure 和 technique）、`mark` 和 `autoMark`、`vanes`（摸高器叶片）、`verdict`、`agreement`、`assess`，不看代码猜不出是什么 | 文件开头一句话说明；重命名留到方案 C |
| 翻译词典 | 中文原句当键（1669 条 × 英德两份），改一个字中文两份译文就对不上 | 短期不动；改稳定键名留到方案 C |
| 规模 | 源码 3.2 万行、测试 1.7 万行、验证工具 4700 行，一个人用的 App | 冻结辅助模块，接手文档里直接说“这些可以先不看” |

还有一处会让新人误判：起跳技术分析是返工最多的模块，但诊断里的“技术”短板其实来自助跑摸高减原地摸高（`dunk.ts` 第 247 行），并不读起跳技术的结果。也就是说，最贵的模块没有接入三问。

## 最慢的 PR

PR 整体不慢：54 个已合并的 PR 里有 37 个在 2 小时内合并，24 个不到 30 分钟。慢的几个全都卡在代码之外。

| PR | 从开到合 | 卡在哪 | 可以怎么优化 |
| --- | --- | --- | --- |
| #59 安全修复 | 开了 12 天还没合 | 要你在 Supabase 做几步一次性操作、再真机验证 | 把不依赖 Supabase 的修复拆出来先合，云端操作单列一张清单 |
| #8 按恢复放宽达标线 | 6.0 天 | 并行包 A–E 规定了串行合并顺序，排在最后 | 并行开发可以，但合并顺序不要依赖人工排队 |
| #9、#10 历史页和训练块 | 各 5.5 天 | 同上，等 #7 先合 | 同上 |
| #7 扣篮诊断 | 5.4 天 | 等你确认方案文档第 7 节的问题 | 可逆的阈值先用默认值合并，问题攒到一张决策卡 |
| #47 没贴线不给数 | 1.5 天 | 等你确认 3 个阈值 | 同上 |

## 返工和共同根因

233 个提交里 93 个是 fix，归成 8 类返工，背后只有两个根因：**R1 没有真实世界的标准答案**，**R2 广度走在深度前面**。两者都来自「问题重新定义」里说的成本不对称。

| 返工 | 规模 | 直接原因 | 根因 |
| --- | --- | --- | --- |
| 起跳技术误差 | 68 个 fix，#45、#47 跨 3 天 | 每轮审查都找到一种没算进去的误差，再加一项，没有停止点 | R1 |
| 识别跳跃 | #21 → #46 → #50 → #54 | 合成视频 48 段过 43 段，真实场景（手机比脚踝高、黑衣服）认不出 | R1 |
| 阈值反复确认 | 几乎每个测量 PR | 让你判断一个没有数据就判断不了的数 | R1 |
| 网页版数据库 | 3 个 fix、#48、#58，另关掉 #49 | 并发启动、半步迁移 | R2：支持了一个不常用也没在真浏览器里测过的平台 |
| 三语译文 | 19 个提交，含 #40 | 中文原句当键，改文案就要补两份 | R2：功能还在变就先做了三语 |
| README 和截图 | README 改 21 次，截图 #39 → #44 重拍 | UI 一改截图就过时 | R2：宣传物料早于功能稳定 |
| 合并冲突 | #19 和 #20 首页冲突，#18 合并后 lint 坏 | 多个线程同时改热点文件（`_layout.tsx` 21 次、首页 17 次、「我的」17 次） | R2：并行线程太多 |
| Git 规则 | squash 改普通合并（#34）、换账号、CLAUDE.md 两处同步 | 规则存在仓库、`D:\claude`、项目记忆三处 | 规则没有唯一来源 |

R1 的表现是：本该看一眼真实数据的地方，用“再加一层代码”或“再问一次你”代替了。R2 的表现是：核心测量还没证明准，就开始扩平台、扩语言、做宣传，之后每次改核心都要连带改一圈。

## 其他领域怎么解这类问题

五个领域都指向同一个答案：**按验证能力限制产出，并且先定合格线再测**。以下数字和概念凭记忆写，没有查证。

| 领域 | 类似的问题 | 他们的做法 | 搬到这里 |
| --- | --- | --- | --- |
| 制造业（约束理论、看板） | 瓶颈前面堆在制品 | 产出由瓶颈决定；给在制品设上限，按瓶颈节拍投料 | 瓶颈是你的真机验证时间；“未验证”的 PR 就是堆积的在制品 |
| 运动科学 | 测一次跳高，变了 2 cm 算不算进步 | 先做信度：典型误差（TE）和最小有意义变化（SWC），变化小于误差不算 | 每个指标标上真实 TE；你差的 2 cm 也要放在误差里看 |
| 医学检验 | 新检测方法能不能上临床 | 先和金标准比（Bland–Altman 一致性分析）；体模过关不等于临床可用 | 合成视频就是体模。摸高墙读数、其他 App 读数、真实扣篮成败才是金标准 |
| 科学研究 | 对同一组数据反复调分析，调到好看为止 | 预注册：先写下合格线和分析方法，再看结果 | 68 个误差 fix 很像对合成场景过拟合。改误差前先写合格线，达到就停 |
| 软件交付（精益创业、功能开关） | 做了不知道有没有用 | 「做—测—学」闭环；“完成”包含真实环境验证；没验证的功能藏在开关后面 | 给指标加验证状态，没验证的可以看，但不进诊断 |

最有用的一个是医学那条：你已经有金标准，就是摸高墙的读数和真实扣篮成败。App 里的一切间接指标，都应该拿来和这两个比。

## 3 版方案

推荐 B。A 便宜但只是写规矩，没有把闭环接上；C 长期最好，但在 12/1 前做等于没有安全网时动大手术。

| 方案 | 你要花的时间 | Claude 工作量 | 解决的根因 | 最大风险 |
| --- | --- | --- | --- | --- |
| A 冻结加规则 | 审 1 个小 PR，10 分钟 | 半天 | R2 的一半 | 规则是文字，线程一多又会被忽略；未验证指标照样进诊断 |
| **B 验证闭环（推荐）** | 下次测试多拍 20 分钟，审 2–3 个小 PR | 约 1 天 | R1 和 R2 | 诊断可能变“空”：验证不了的指标会被标成仅供参考 |
| C 全面重构 | 审大 diff，数小时 | 3–5 天 | R1、R2 和接手成本 | 重构期间引入回归，占用你冲刺期的注意力；违反 CLAUDE.md 第 3 条 |

### A 冻结加规则（半天）

- 12/1 前只修 bug，不加功能。
- CLAUDE.md 加 3 条：测量类 PR 写清验证状态；改误差或阈值前先写合格线；可逆阈值先用默认值合并，确认攒到一张卡。
- 关掉 npm 依赖自动升级，关掉 3 个没人处理的依赖 PR。
- 二阶影响：你不用再审 PR，注意力回到训练。三阶影响：规则只靠自觉，下一波并行线程来时会失效。

### B 验证闭环（约 1 天，推荐）

A 的全部，再加：

1. **一次搭便车的真机验证**：下次你本来就要测摸高时，按已有清单多拍一轮（摸高 3 次、CMJ 5 次、深蹲 1 组），墙上读数写进 `读数.txt`。我用 `tools/` 下现有脚本跑真实视频，出一张误差表。
2. **指标带验证状态**：metrics 注册表加一个字段，标“真机验证过 / 只有合成验证”。只有合成验证的指标照样显示，但标“仅供参考”，不参与“差在哪块”。这改了诊断行为，按规则会先等你确认。
3. **真实数据进 CI**：视频不进仓库（隐私），只存从中提取的骨架点和像素轨迹加你的读数，作为准确度回归的第一组真实基线。
4. **一个「真机验证」 Skill**：告诉以后的 Claude 线程，测量 PR 怎么出拍摄清单、怎么跑脚本、怎么判合格。
5. **清掉无害包袱**：coverage 文件、过期设计文档。
6. **拆 #59**：不依赖 Supabase 的修复先合，云端操作单列。

- 二阶影响：诊断可能只能给出部分答案，这是诚实的代价；你拍一次就能解锁好几个指标，验证变成有回报的事。无法找到参照的指标（例如杠铃速度：你手上的 Metric 导出不能当参照）会一直标着“仅供参考”。
- 三阶影响：推广时可以拿出一张真实误差表，比功能列表更有说服力；以后新加的测量自带验证状态，返工在前面就被拦住。维护成本只是多一个字段、一个 Skill。

### C 全面重构（3–5 天）

B 的全部，再加：`domain/` 按三问分目录、拆 `technique.ts`、翻译改成稳定键名、网页版数据库和团队模式移出主干、仓库里补决策记录和接手文档。

- 二阶影响：几千行的 diff 要你看，而且是在还没做真机验证、没有安全网的时候。三阶影响：长期接手成本最低，推广时代码最好看。
- 建议：等 12/1 之后，如果还要推广到队内，再拆成小 PR 分批做。

## 先假设 B 是错的

站在最强反对者的角度，有 6 条能动摇 B。其中 3 条成立并改进了方案，1 条部分成立，2 条不改变结论。

| 反对理由 | 成立吗 | 对方案的修正 |
| --- | --- | --- |
| 差 2 cm 已在摸高误差内，任何测量都答不了“还差多少” | 成立 | 把**真实扣篮尝试的成败**当最高级的标准答案（App 已有记录，#24）。摸高进入误差带后，首页主看最近几次扣进几个 |
| “未验证不准合并”会让开发停摆，因为验证产能接近 0 | 成立 | 不设合并门槛，只设**显示门槛**：可以合、可以看，但不进诊断 |
| 你可能根本不想再专门拍验证视频 | 成立 | 验证搭在本来就要做的测试上，不另约时间；拍不了就保持“仅供参考”，不影响你训练 |
| 规则会越积越多，CLAUDE.md 膨胀后没人看 | 部分成立 | 这次只加 3 条，并把能做成 CI 的改成 CI；「12/1 前冻结」写上到期日，到期删除 |
| 冻结功能会让推广和宣传停下 | 不成立 | 推广靠可信度，一张真实误差表比新功能有用；12/1 后就解冻 |
| 合成验证并非没用，它拦住过不少退步 | 成立，但不冲突 | 保留合成回归 CI，只是不再把它当成“准”的证据 |

还有一个边界情况：如果真机验证结果很差（比如 CMJ 误差大到分不出进步），诊断的“差在哪块”会基本留空。那也是有用的结论：说明应该先修那个测量，而不是继续加功能。

**重新评估后**：B 保留，并吸收上面 3 条修正：只设显示门槛；真实扣篮成败作为最高标准；验证搭在已有测试上。

## 沉淀成规则、自动化和 Skill
